# Volyx

**Marks in. Report cards out.**

Volyx is a web app built on the [GradeScriptUG](https://gradescriptug.com) marking API. Teachers upload handwritten scripts, GradeScriptUG marks them, and Volyx turns those marks into official report cards that students open by signing in with their **school email**.

```
Teacher uploads pages ──▶ POST /grading ──▶ polled until graded
                                                  │
                                    marks → grades → report card
                                                  │
              Student signs in by email ──▶ opens their terminal report
```

---

## Run it

```bash
cd gradescript-portal
npm start          # no dependencies to install
```

Open <http://localhost:3000>.

### Accounts

Volyx is multi-tenant: **every teacher owns their own students**, and nobody can see anybody else's.
There are three roles — **admin**, **teacher** and **student**. See [Roles](#roles-rbac).

You choose your role when you sign up:

| | Teacher | Student |
|---|---|---|
| Sign up as | *Teacher* | *Student* |
| Lands on | the console (`#/teacher`) | the portal (`#/portal`) |
| Grades scripts | ✅ | ❌ |
| Sees results | only their own accounts' | every teacher who used their email |

| Account | Email | Password |
|---|---|---|
| **Platform admin** | `ryanroject@gmail.com` | `volyx-admin-2026` |
| Demo teacher | `robert.wamala@gmail.com` | `volyx1234` |

Both start with zero students. Change the admin password after the first sign-in — the address in
`config/school.js` (`PLATFORM_ADMIN_EMAIL`) is what makes that account the administrator, so signing up or
using Google with it is enough to take it over.

**No mail server is configured out of the box**, so verification codes are shown on screen and printed in the
server log (clearly marked as development). Set `RESEND_API_KEY` to deliver real email — see `lib/mailer.js`.

### The platform key

There is **one GradeScriptUG key for the whole platform**, and only the administrator can set it:

1. Sign in as `ryanroject@gmail.com` → **Platform** (or Settings).
2. Paste the key → **Verify & save**. It is checked against the API, then stored server-side.
3. Every teacher's upload now runs on that key. Teachers never see it, never type it, and get a `403` if they try.

```
POST   /api/admin/key       admin only — verify + store the platform key
DELETE /api/admin/key       admin only — disconnect (whole platform → demo mode)
GET    /api/admin/overview  admin only — key state + platform counts
```

`GRADESCRIPT_API_KEY` in the environment takes priority over the stored key.

### Grading by email (how work reaches a student)

A script is uploaded **for an email address**, not for a private student record:

| Field | Required | Notes |
|---|---|---|
| `studentEmail` | ✅ | The address the marks belong to. This is the join between a teacher and a student account. |
| `studentName` | — | Derived from the address if omitted; auto-filled from a saved student. |
| `subject` | ✅ | Per the API docs. |
| `assessmentType`, `termId`, `level`, `instructions` | — | Per the API docs. |
| `attachments[n][file]` + `type` | ✅ | At least one `SCRIPT`; optional `MARKING_GUIDE`. |

Picking one of your saved students fills the email automatically. Grading then continues in the background
(`POST /grading` → `202` → poll `GET /grading/{id}`) and the finished marks are filed under that address.

**Any teacher can grade the same student.** When someone signs up as a *Student* with that address, their
portal shows everything addressed to it — from every teacher, with the marking teacher named per subject.
No publishing step is required; work appears as soon as it is marked.

A student account matches on **either** its login address or the contact email on a linked student record, so
a login generated by a teacher (`amina.nakato@students.volyx.ug`) also sees work addressed to
`amina.nakato@gmail.com`.

### Auth endpoints

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/api/auth/signup` | create an account, sends the first 6-digit code |
| `POST` | `/api/auth/request-code` | **email me a code** — sends a code (`purpose: verify` while unconfirmed, `login` once verified) |
| `POST` | `/api/auth/verify-code` | finish a code sign-in, and activate the account if it wasn't confirmed |
| `POST` | `/api/auth/verify-email` | confirm a signup with its code |
| `POST` | `/api/auth/resend-code` | alias of `request-code` (kept for older clients) |
| `POST` | `/api/auth/login` | email + password |
| `POST` | `/api/auth/forgot` · `/api/auth/reset` | password reset by code |
| `POST` | `/api/auth/google` | Continue with Google |
| `POST` | `/api/auth/logout` | clear the session |

Codes are 6 digits, hashed at rest, single-use, expire in 15 minutes, and are rate limited to 5 requests
per email per 10 minutes. `{ok, purpose, delivery:{devCode}}` comes back with `devCode` only when no mailer
is configured.

### Roles (RBAC)

Three roles, decided at sign-up, enforced on every request:

| Role | Who | Can do | Lands on |
|---|---|---|---|
| **Admin** | `ryanroject@gmail.com` only | everything a teacher can do, **plus** the one platform API key | `#/teacher` + **Platform** tab |
| **Teacher** | anyone who signs up as a teacher | students, uploads, publishing, own settings | `#/teacher` |
| **Student** | anyone who signs up as a student | read-only: work addressed to their email, from any teacher | `#/portal` |

A single gate in `server.js` (`rbacGate`) runs before any route:

* a **student session** may only touch `/api/student/*`, `/api/me`, `/api/config` and `/api/auth/*` —
  anything else is `403 {code:'read-only-role'}`;
* a **teacher/admin session** cannot enter `/api/student/*` (`403 {code:'teacher-not-student'}`);
* `/api/admin/*` is `403 {code:'admin-only'}` for anyone but the administrator;
* the browser router applies the same rules, so a student who types `#/teacher/students` is bounced to
  `#/portal`, a teacher who types `#/portal` is bounced to `#/teacher`, and `#/admin` is admin-only.

The portal is read-only by construction: there is no write endpoint under `/api/student/*`, and the UI renders
no edit affordances.

### Data isolation

Every student row carries an `ownerId`. Every route resolves the owner from the session and filters by it:

| Request | Behaviour |
|---|---|
| `GET /api/students` | the caller's students only |
| `PATCH/DELETE /api/students/:id` | `404` unless the caller owns that student |
| `GET /api/teacher/gradings/:id` | `404` for another account's grading |
| `POST /api/teacher/publish` | publisher list is stored per owner (`term.published[ownerId]`) |
| `GET /api/student/report/:term` | the signed-in student's own record, once its owner publishes |

### Student logins (generated automatically)

Adding a student **mints a login for them** — the teacher never invents a username:

```
amina.nakato@students.volyx.ug     ← from the student's name, deduplicated
Vx-k4tq-m9rz-27                    ← temporary password, shown once
```

* The password is stored **only as a scrypt hash**. It is returned in the response that creates
  or rotates it, and never again — "Issue a new password" replaces it.
* Both actions sign the student out of any open session (credential rotation ends sessions).
* The teacher gets a **Login** button per student: copy the details, email them, or reissue.
  Emailing sends them to the student's contact address via `lib/mailer.js` (dev mode shows them on screen).
* First sign-in flags `mustChangePassword`, so the portal nudges them to pick their own password
  (`POST /api/auth/change-password` — the only write a student account can make).
* Deleting a student profile deletes the login that belonged to it.

A student who prefers their own address can sign up as a student (or use Google) with any address a teacher
has on file; that login sees the same marks as the generated one.

### Credential & portal endpoints

| Method | Path | Role | Purpose |
|---|---|---|---|
| `POST` | `/api/students` | teacher | create a student **and** their login (returns `credentials` once) |
| `GET` | `/api/students/:id/credentials` | teacher (owner only) | status: address, whether the temp password is live, sessions, last sign-in |
| `POST` | `/api/students/:id/credentials` | teacher (owner only) | rotate the temporary password, return it once |
| `POST` | `/api/students/:id/credentials/email` | teacher (owner only) | rotate and email the details to the student's contact address |
| `POST` | `/api/auth/change-password` | any signed-in account | replace own password (clears `mustChangePassword`) |
| `GET` | `/api/student/me` | student | own addresses, the teachers who marked them, permissions |
| `GET` | `/api/student/results` | student | every marked script addressed to their email, with the teacher named |
| `GET` | `/api/student/assessments` | student | alias of `/results` |
| `GET` | `/api/student/terms` | student | terms that have marks for this student |
| `GET` | `/api/student/report/:term` | student | report card combining **all** teachers for that term |
| `GET` | `/api/student/results/:id` | student | one marked script: marks, questions, feedback, `pages[]`, annotations |
| `GET` | `/api/student/results/:id/pages/:n` | student | the stored page image the annotations are drawn over |
| `GET` | `/api/teacher/gradings/:id` | teacher (owner only) | same payload for the teacher's own script |
| `GET` | `/api/teacher/gradings/:id/pages/:n` | teacher (owner only) | page image for the teacher's own script |

No endpoint returns a password hash, and `GET …/credentials` never returns a plaintext password.

## Turn on Sign in with Google

1. <https://console.cloud.google.com> → create (or pick) a project.
2. **APIs & Services → OAuth consent screen** → External → add your school domain and any test users.
3. **APIs & Services → Credentials → Create credentials → OAuth client ID → Web application**.
4. Add **Authorised JavaScript origins**:
   - `http://localhost:3000`
   - your production URL, e.g. `https://results.yourschool.ac.ug`
   (no redirect URI is needed — Volyx uses the Google Identity Services button, not a redirect flow)
5. Copy the Client ID (it ends in `.apps.googleusercontent.com`).
6. In Volyx, sign in as a teacher → **API key → Sign-in** → paste → **Save Client ID**.
   (Or set the `GOOGLE_CLIENT_ID` environment variable — the env value wins.)

The server verifies every Google credential with Google before trusting it: signature/issuer, audience
match, expiry, and `email_verified`. A Google token minted for another app is rejected.

> In this chat's preview iframe, Google's script is blocked (no external network in the sandbox), so the
> button falls back to the email-code message. Both paths work the same once you run it on a real host.

## Connect the real GradeScriptUG API

1. In the GradeScriptUG console pick your organization → **API keys → Create API key**
   (permissions: *Create gradings* + *View gradings*; add *Edit gradings* to retry failed scripts from here).
2. In Volyx, sign in as the **administrator** (`ryanroject@gmail.com`) → **Platform** → paste →
   **Verify & save**. One key now serves every teacher; teachers cannot see or change it.

New uploads now go to `https://api.gradescriptug.com/client/v1` and come back marked.

For production keep the key in the environment instead of the database:

```bash
GRADESCRIPT_API_KEY=gsk_3f9a1c2e_5b8d0e7f… npm start
```

> **Why the key is not in the browser.** The docs are explicit: *"The API only accepts browser requests from GradeScriptUG's own sites, so a key used in front-end code fails anyway, and anyone could copy it."* Volyx proxies every call through the Node server; the browser only ever sees `gsk_3f9a1c2e••••`.

## The marked work — see how it was marked

The API returns marks, never images ("your frontend draws on its own copy of each page").
So Volyx keeps that copy and draws the marker's annotations over it.

- **Page store.** Every `SCRIPT` file of an upload is written to `data/uploads/<gradingId>/`
  (`lib/storage.js`), and `pages[]` is recorded on the grading (`index`, `file`, `kind`, `filename`).
  Marking guides are not kept. `data/` is gitignored and is deleted with the grading
  (`DELETE /api/teacher/gradings/:id`, *clear results*, *reset demo*).
- **Serving.** `GET /api/teacher/gradings/:id/pages/:n` (owner only) and
  `GET /api/student/results/:id/pages/:n` (any teacher's grading addressed to one of the
  student's emails). Both `404` rather than `403` for someone else's script.
- **One script in full.** `GET /api/teacher/gradings/:id` and `GET /api/student/results/:id`
  return the marks, `questions[]`, `feedback`, `pages[]`, and every annotation with the page it
  belongs to (`pageIndex`, resolved from `attachmentID` over script files only).
- **Drawing.** `public/app.js → markedScriptHTML()` renders
  `<div class="page-frame"><img><svg class="marks-layer"></svg></div>`; `drawMarks()` sets the
  SVG `viewBox` to the page's pixel size and draws each annotation:

  | Type | Drawn as |
  |---|---|
  | `TICK` / `CROSS` / `PARTIAL` | stroked path in the 24×24 glyph box, at the right end of the box, mid-height, `#d32f2f` |
  | `PARTIAL` | tick plus a short slash (the docs' "partly correct" glyph) |
  | `COMMENT` | the comment text in the right margin |
  | `MARK` | `awarded/max`, e.g. `3/6`, in the right margin |
  | `BLANK` / `CROSSED_OUT` | one diagonal stroke across the box |
  | any + `needsReview` | a circled `?` beside the box, with `reviewReason` in the question table |

  Sizes are a share of the page width (glyph 4.5%, text 2.3%) so they hold at any zoom, and
  anything with `x ≥ 0.9` is placed in the right margin as the docs specify. Fractions mean the
  marks can be laid out before the image arrives; they are redrawn at the real pixel size on `load`.
- **How the grade was worked out.** Next to the pages, *How this was graded* shows the arithmetic
  from `config/school.js`: `marks ÷ possible = percent → band`, the band's range, label and points,
  how many more marks the next band needed, which question cost the most, how many questions earned
  full marks, and a cross-check that the question marks add up to the recorded total.
- **Question ⇄ mark linking.** Every drawn mark is grouped under its `questionRef`. Clicking a row in
  *How each question was marked* spotlights that question's marks (a dashed box appears on the page,
  everything else dims, the page scrolls into view and flashes); click again or press `Esc` to clear.
- **Where it lives.** Teacher: **Marked work** tab → `#/teacher/grading/:id`. Student:
  `#/portal/result/:id`, linked from *My marks*. Both show the marks over the pages next to the
  per-question mark/why table, the marker's feedback and any ⚑ flags, and print cleanly.
- **Not drawn:** PDF pages (no PDF renderer in the browser build). They get an *Open the PDF*
  card with the marks for that page listed underneath. Images (PNG/JPEG/WEBP) draw fully.
  Scripts uploaded before this feature have no stored pages and show a "page copy not kept" state.

## Where each part of the docs landed

| Doc page | Implementation |
|---|---|
| **Authentication** — `Authorization: Bearer gsk_…` | `lib/gradescript.js → call()`; key in `data/db.json` or `GRADESCRIPT_API_KEY` |
| Key format `gsk_<8 hex>_<32 hex>` | `looksValidKey()`, checked before saving |
| Keys must stay on a server | All traffic proxied in `server.js`; only `keyHint()` is serialised to the client |
| `401` / `403` permission messages | Surfaced verbatim in the API key panel and upload errors |
| **Submitting scripts** — `multipart/form-data`, `attachments[N][type|index|file]` | `POST /api/teacher/gradings` → `createGrading()` rebuilds the form for the API |
| `studentFullname`, `subject` required; `level`, `assessmentType`, `instructions` | Taken from the school register so they can't be mistyped |
| `SCRIPT` / `MARKING_GUIDE` / `QUESTION_PAPER` / `OTHER` | Upload form sends script pages + an optional marking guide |
| Limits: 20 files, 20 MB each, 60 MB/request, 40 pages, PDF/PNG/JPEG/WEBP | Validated server-side with the docs' own wording |
| **Tracking progress** — `PENDING → PROCESSING → COMPLETED/PARTIAL/FAILED` | Status badges; polling every 6s; `PARTIAL`/`FAILED` show `error` |
| Poll every 5–10s; no webhooks | `setInterval` refresher + **Refresh** button |
| Retry (`Edit gradings` permission) | Retry on failed gradings |
| **Reading results** — `totalMark` / `maximumMark`, `questions[]` | Report rows and the per-question breakdown |
| `rationale`, `needsReview`, `reviewReason`, `graded: false` | Shown per question with a ⚑ flag and counted as "needs review" |
| `feedback` — plain text for the student | Shown under each assessment |
| `annotations` (fractional coordinates, tick/cross/mark types) | Stored with every grading and drawn over the student's own page — see **The marked work** below |

Only `COMPLETED` and `PARTIAL` gradings count toward a report card; `PARTIAL` rows are labelled *provisional*.

## Report card maths

Everything lives in `config/school.js`:

- **Subject %** = total awarded ÷ total available across that subject's scripts in the term
- **Grade / points** — UNEB-style: A 80–100 (1 pt), B 70–79 (2), C 60–69 (3), D 50–59 (4), E 40–49 (5), F 0–39 (9)
- **Aggregate** = sum of the best 8 subject points (lower is better)
- **Division** — I ≤ 24, II ≤ 36, III ≤ 48, IV ≤ 60, otherwise U
- **Position** = rank by average % among classmates with at least one graded script that term
- **Comments** are generated from the average, best/worst subject and position (deterministic — swap `teacherComment()` in `lib/report.js` for a model call if you want one)

Change the platform name, school, motto, classes, subjects, terms and scale in `config/school.js` (`PLATFORM` and `SCHOOL` blocks).

## Not built yet

- **Drawing marks on PDF scripts.** PDF pages are kept and can be opened, but the browser build has no PDF rasteriser, so their marks are listed rather than drawn. Upload PNG/JPEG/WEBP pages (or add `pdf.js`) to get the overlay on every page.
- **Real email delivery.** Codes appear on screen and in the server log. Add SMTP/Resend inside `POST /api/auth/request-code` and drop `demoCode` from the response (`SMTP_URL` is stubbed in `.env.example`). Google sign-in needs no email at all, so wiring SMTP is only needed for users without a Google account.
- **Email change / account deletion.** Users can reset a password but not yet change the email on an account.
- **Password-strength policy for students.** The generated passwords are read-aloud friendly, not memorable;
  students are nudged to replace them on first sign-in but not forced to.
- **Per-teacher sub-keys.** One platform key is shared by every teacher; if you need per-school billing or
  revocation you would issue keys per organisation instead (the `settings.apiKey` field is the seam).
- **A real database.** `data/db.json` is fine for a class, not a school — swap `lib/db.js` for Postgres/SQLite; the rest of the code only touches `db().students`, `.gradings`, `.terms`, `.sessions`.

## If a grading won't queue

The upload form now states the reason in place, keeps your files attached and lets you press
**Queue grading** again — nothing is lost. What each message means:

| What you see | What to do |
|---|---|
| **Cannot reach the Volyx server** | The app restarted or the connection dropped. It retries once by itself; press **Queue grading** again — the pages are still attached. |
| *"… must be a PDF, PNG, JPEG or WEBP file"* | The marker only reads those. Any other **photo** (HEIC, GIF, BMP, TIFF) is converted to PNG in the browser automatically; documents (`.docx`, `.txt`) have to be exported to PDF first. |
| *"Add the student's email first"* | Every grading is addressed to an email — that is how the marked work reaches the student. |
| *"That does not look like an email address"* | Check the address; there is no need to add the student to your list first. |
| *"over 20 MB"* / *413* | One file per page, under 20 MB each, 60 MB per upload. Photograph fewer pages per upload. |
| *"Invalid API key"* or *"Could not reach GradeScriptUG"* | The platform key is set but GradeScriptUG refuses it. The admin reconnects the key under **Platform**; until then nothing can be marked live. |
| Grading queued but stuck on *Processing* | Demo mode advances by itself every 5 s. Live mode polls GradeScriptUG every 15 s; press **Refresh** on the overview. |

The server also keeps itself alive: the demo/live pollers and every request are wrapped so a single
bad record or a network blip cannot take the process down mid-upload.

## Production checklist

- Serve over HTTPS and set `NODE_ENV=production` (the session cookie becomes `Secure`)
- `data/uploads/` holds students' scripts — treat it like exam papers (backups, retention, access)
- Keep `data/` out of version control — it holds sessions (`.gitignore` covers it)
- One API key per environment, with an expiry date, so you can revoke one without breaking the others
